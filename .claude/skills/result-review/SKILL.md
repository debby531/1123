# 結果檢討

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「看到什麼現象 → 代表什麼問題 → 下一次怎麼改」，讓 AI 像店長一樣檢討。

## 什麼時候用

每跑完一次 `npm run simulate`，要決定下一版策略怎麼改時。

## 試算結果裡有哪些線索

試算工具每天會印出：客人數、收入、備貨、宣傳、報廢（清潔費）、淨利、任務、星等、資金，以及「沒買到的客人」：

| 線索 | 意思 |
|---|---|
| 賣完買不到 | 有人想買，但貨不夠 |
| 嫌太貴 | 價格超過客人剩下的預算 |
| 想吃的沒上架 | 客人想吃的菜今天沒賣 |
| 因為討厭的菜不進門 | 上架了某位客人討厭的菜 |

## 對症下藥表

| 看到的現象 | 代表的問題 | 下一次怎麼改 |
|---|---|---|
| 賣完買不到很多 | 備貨太少 | 那樣菜多備一些（注意合計不能超過 80 份） |
| 報廢 15 份以上 | 備貨明顯超過需求（推測：份數抓太多，或定價/菜單組合跟這天客群不合導致賣不掉；要對照「賣出」與「賣完後沒買到」確認是不是真的備太多，不是單純賣不掉） | 那樣菜份數往下調，調到接近倉庫盤點的「明天建議備貨」（賣出＋賣完後沒買到），一次只調這一樣，不要同時砍好幾樣 |
| 嫌太貴很多 | 價格超過客人剩下的預算，買不起；或定價超過建議售價太多，讓本來會「滿意」的人變成「普通」 | 把那樣菜的價格調低一點，但先看「嫌太貴」跟「滿意／普通」的人數比例再決定調多少；降價前比照 pricing-rules 心法 1，要有這種實際觀察支持才降，不要用感覺降價 |
| 想吃的沒上架很多 | 推測：這天客群最想吃的菜，沒被選進當天最多 4 樣的上架名單裡，菜單組合跟客群不合（實際原因要對照客人包內容才能確定，不要用猜的） | 下一版換一下上架的 4 樣組合；如果不知道客人想吃什麼，先記錄「這天想吃的沒上架」出現在哪幾天，再嘗試不同組合比較結果 |
| 因為討厭的菜不進門 | 推測：上架的菜裡有這群客人討厭的，客人看到就直接不進店（不會留下評價，規則書：討厭的東西有上架就不進門） | 如果知道討厭哪一樣，下一版避開、換其他菜上架；如果不確定是哪樣，先記錄「這天進店人數異常少」當線索，不要亂猜著改 |
| 星等往下掉 | 依規則書：滿意比例 < 30% 或不滿比例 ≥ 25% 時 −0.5 顆，滿意 < 15% 或不滿 ≥ 40% 時 −1 顆，代表當天客人整體買得不順利（嫌太貴、缺貨、菜單不合其中一種或多種同時發生） | 回頭看同一天滿意／普通／不滿的人數，先找出造成最多「不滿」的那個原因（缺貨？太貴？菜單不合？），一次只改一個，才知道是哪個改動有效 |
| 宣傳後增加來客，但淨利未改善 | 先核對實際觀察（不要先下結論）：①來客數是否真的照規則書的宣傳加成變多（200 元 +20%、500 元 +45%）；②新增的客人有沒有真的買到東西（還是來了但嫌太貴／缺貨／不滿）；③新增的營業收入夠不夠蓋過宣傳費本身，加上這些新客人額外吃掉的備貨成本與可能增加的報廢清潔費 | 如果是因為備貨不夠接住變多的客人（缺貨）：先把備貨提高再搭配宣傳；如果備貨足夠、客人也買到了，淨利還是沒提升：代表這次宣傳的投入報酬不划算，下一版把宣傳費調回較低一檔（或 0 元），改成只調整備貨或定價，單獨看效果 |

## 步驟

1. 讀試算結果，逐天找出上表的現象
2. 每一個現象，照對症下藥表提出一個修改
3. **一次最多改 3 個地方**，這樣才知道是哪個修改有效
4. 把修改後的策略存成新的檔案（例如 `plans/v2.json`），不要覆蓋舊的，方便比較

## 回報格式

```text
這一版的結果：最終資金 …、星等 …、報廢 …
發現的問題：
1. 第 N 天：（現象）→（問題）
修改：
1. …
下一版檔名：
```

## 不准做的事

- 不准修改遊戲檔案（`src/` 底下的任何檔案、客人包）
- 只能新增或修改 `web-lab/plans/` 裡的策略檔
