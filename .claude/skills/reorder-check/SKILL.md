# 補貨檢查

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「數字一定要從盤點資料抄，不能自己編」，而且每個數字都要能驗算。

## 什麼時候用

- 跑完 `npm run simulate`，要決定下一版策略每樣菜備幾份時
- 在瀏覽器玩完一天，想看「倉庫盤點」頁的結果該怎麼調整時

## 資料從哪裡來

在 `web-lab` 資料夾執行：

```text
npm run simulate -- plans/策略檔.json --json
```

每一天的 `inventory` 欄位，是那天每樣上架的菜的盤點：

| 欄位 | 意思 | 怎麼驗算 |
|---|---|---|
| `name` | 菜名 | — |
| `stocked` | 早上備了幾份 | 策略檔裡的 `qty` |
| `sold` | 賣出幾份 | 打烊報表 |
| `waste` | 報廢幾份 | 備貨 − 賣出 |
| `missed` | 賣完之後，還有幾位客人想買卻沒買到 | 客人卡片上「賣完了」的數量 |
| `status` | `ok` 正常、`out` 缺貨、`over` 報廢過多 | 規則書「倉庫盤點」 |
| `suggest` | 明天建議備幾份 | 賣出 ＋ 沒買到 |

## 步驟

1. 執行上面的指令，讀每一天的 `inventory`
2. 先驗算：`waste` 有沒有等於 `stocked − sold`？對不上就停下來回報，**不要用錯的資料做建議**
3. 挑出 `status` 不是 `ok` 的菜
4. 基礎建議量＝賣出＋沒買到（規則書公式），不直接加固定比例。缺貨（`out`）的菜：只有盤點資料裡有具體證據（例如連續幾天都缺貨、策略檔寫了隔天要加碼宣傳）才在基礎量之上再往上調整，並寫出調整了多少、為什麼；沒有證據就只給基礎量。報廢過多（`over`）的菜：往下調整到接近「賣出＋沒買到」，同樣要寫原因。不准憑感覺加減或編造需求數字。
5. 同一道菜連續 2 天以上都是 `out` 或 `over`，要特別提醒：列出每一天的第幾天、實際數量（備貨／賣出／報廢或沒買到），並指出可能的經營問題（例如一直備太少或備太多，不是單日運氣不好）。只有一天資料時，不可以判斷為連續異常，只能就那一天的狀態提建議。
6. 用下面的回報格式回報

## 回報格式

```text
策略檔：
驗算結果：通過 / 第 N 天的 ○○ 對不上（寫出哪個數字）
第 N 天：
  缺貨：菜名 備 … 賣 … 沒買到 … → 建議 …
  報廢過多：菜名 備 … 賣 … 報廢 … → 建議 …
每一樣被列出的菜，除了備／賣／報廢或沒買到的數字，再加：異常原因（為什麼缺貨或報廢過多）、建議備貨量（基礎量，有調整的話是調整後的量）、計算依據（算式，例如 賣出8＋沒買到2＝10）、調整理由（有沒有再往上/往下調，為什麼；沒調整就寫「無」）：
下一版每天建議的備貨量：
```

## 寫完檢查

- [ ] 每一個數字都能在盤點資料裡找到
- [ ] 每個數字是不是非負整數；賣出有沒有超過備貨；報廢是否等於備貨 − 賣出；狀態（缺貨／報廢過多／正常）與「明天建議備貨」是否符合規則書（`docs/RULES.md`「倉庫盤點」）的定義
- [ ] 資料缺漏或互相矛盾時，有沒有寫出是哪一天、哪樣菜、哪個欄位出問題，並只暫停那一筆的備貨建議（其他數字沒問題的菜照常分析）

## 不准做的事

- 不准修改任何檔案（這個 Skill 只讀不寫，要改策略交給 result-review）
- 不准自己編數字，或用「大概」、「差不多」帶過
- 原始數字一律照抄盤點資料或本檔列出的資料來源，不准自行估算；計算出來的數字（報廢、建議備貨量等）都要寫出算式，不能只給結果
